# Resource selection contract

`detectResources()` reads Linux cgroup v2 current/ancestor cpu.max, memory.max/high/current, affinity-aware `os.availableParallelism()`, total memory and MemAvailable. Root cgroup has no quota controller files and is not treated as a child limit. For missing child controller files, it verifies that the child still exists and that the parent has not enabled that controller, then continues reading ancestor limits. Missing files with the controller enabled, unreadable metadata, and malformed limits still fail instead of assuming unlimited capacity. Ancestor details accompany the result. Missing cgroup namespace mount translation is unsupported; callers must report detection errors.

`selectResources(input, env)` is pure. CPU defaults to half effective capacity. Reserve is one quarter of physical memory bounded between 1 and 8 GiB. Maximum is bounded by half total memory, available minus reserve, and 80% of ancestor remaining headroom. High is 75% of selected max, rounded down to 64 MiB. Worker estimate uses one per four allocated CPUs and 2 GiB high budget, with at least one; no swap, TasksMax1024. Less than 512MiB safe budget refuses execution. This is a conservative initial policy, not a promise that arbitrary test workloads fit.

Overrides are positive integer strings: BB_RESOURCE_CPU_QUOTA_PERCENT, BB_RESOURCE_MEMORY_HIGH_BYTES, BB_RESOURCE_MEMORY_MAX_BYTES, BB_RESOURCE_VITEST_WORKERS. They are validated against effective CPU, memory headroom and reserve; unsafe overrides fail. They do not silently raise ancestor limits. No task is launched and no systemd properties change here.

Run `node scripts/resource-profile.mjs` for JSON `{detected, selected}` and `node --test scripts/resource-profile.test.mjs` for light behavioural fixtures. For synthetic 32 CPU/62GiB total/42GiB available with unlimited ancestors: CPU1600%, max31GiB, high23.25GiB, workers4. For 2CPU/4GiB total/2GiB available: CPU100%, max1GiB, high0.75GiB, workers1. Actual output changes with available memory and effective ancestor limits; no assumption that a future host has 32 CPUs or 64GiB.

The flow wrapper author owns integration: detect before creating its new scope (not inside the old fixed-limit scope), set and verify actual properties, apply concurrency to each resolved Vitest project, keep a single job and cancellation/cleanup contract. CLI/root maxWorkers alone may not override project-level values. Detection is a snapshot, not memory reservation; scope MemoryMax/no-swap remains mandatory after selection. Concurrent external allocations and host IO pressure remain noise. Wrapper, AGENTS and build workbook are deliberately unchanged.
